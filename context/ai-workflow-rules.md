# Development Workflow

## Approach

Build incrementally using a spec-driven workflow. Context files define what to build, how to build it, and the current state. Implement against these specs and do not invent behavior.

## Scoping Rules

- Work on one feature unit at a time.
- Prefer small, verifiable increments.
- Do not combine unrelated boundaries in one step.

## When To Split Work

Split a step if it combines:

- Web app changes and ML changes
- Model training and API integration
- UI changes and database schema changes
- Behavior not clearly defined in the context files

If a change cannot be verified end to end quickly, it is too broad.

## Handling Missing Requirements

- Do not invent product behavior.
- If a requirement is ambiguous, resolve it in the relevant context file first.
- If it is missing, add it to Open Questions in `progress-tracker.md` before continuing.

## ML-Specific Rules

- **Test split is off limits.** No agent reads, previews, or computes on it. Only `ml/eval/final_eval.py` uses it, once, after choices are frozen.
- **Human-written core.** The author writes the split logic, similarity scoring, and the evaluation script. The agent may explain, review, and suggest edge cases, but does not generate these files.
- **Explain before accept.** For any ML code the agent writes, it first explains what the code does, why this approach, the alternatives, and what could go wrong (leakage, wrong metric, bad split).
- **Decision log.** Every modeling choice (dataset, split, features, model, threshold) gets an entry: decision, alternatives, reason, date.
- **Results discipline.** Every results table includes the mean baseline. Report which split each number came from. Never report a number that cannot be regenerated by a script in the repo.
- **No silent tuning.** Hyperparameter changes are tried on validation only and logged.

## Protected Foundation Components

Do not modify `components/ui/*` (shadcn/ui) or third-party library internals unless explicitly instructed. Put project styling and logic in app-level components.

## Keeping Docs In Sync

Update the relevant context file when implementation changes architecture, storage, standards, ML setup, or scope. Progress state must reflect the actual state, not the intended state.

## Before Moving To The Next Unit

1. The current unit works end to end within its scope.
2. No invariant in `architecture-context.md` was violated.
3. The decision log and `progress-tracker.md` are updated.
4. The author can explain what was built.
